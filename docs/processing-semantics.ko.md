# 처리·복구·종료 동작

> [English](processing-semantics.md) · **한국어** · [샘플 안내](../samples/README.ko.md)

현재 저장소 구현을 기준으로 설명한다. [변경 내역](../CHANGELOG.md)의 **Unreleased** 항목은
설치한 NuGet 버전에 아직 포함되지 않았을 수 있다.

## 게시와 백프레셔

슬롯 점유는 트랜잭션이 아니다. `Next()` 이후에는 `finally`에서 `Publish()`하거나 좁은 범위의
`PublishEventScope()`를 사용한다. scope·translator·`PublishGate`는 작성 중 예외가 나도 게시한다.
입력 검증은 점유 전에 끝내고, 작성 실패 가능성이 있으면 불완전한 이벤트를 구별하는 상태를 둔다.

| `PublishGate` 정책 | 용량 확보 방식 | 결과 |
|---|---|---|
| `Block` | 취소 가능한 `Next` 호출, 생산자 백오프 설정 적용 | 게시 후 `true`; 취소·백오프에 따라 예외 발생 가능 |
| `DropWhenCongested` | 사용률 검사 후 점유 시도, 소비자가 공간을 비울 때까지 기다리지 않음 | 혼잡·용량 부족 시 `false`, `DroppedCount` 증가 |
| `FailAfterTimeout` | 제한 시간까지 호출 스레드에서 동기 재시도, 기본 50ms | 시간 초과 시 `false`, `RejectedCount` 증가 |

`TryPublish`의 `cancellationToken`은 `Block`에만 적용된다. `FailAfterTimeout`은 호출 스레드를
점유하며 타임아웃은 실시간 스케줄링 상한 보장이 아니다. 드롭 정책은 최신값 병합 기능이 아니다.
`true`는 게시 성공이며 소비 완료·영구 저장 완료를 뜻하지 않는다. 작성 예외는 게시 후에도 호출자에게 전파된다.

## 동기 예외 정책

| 핸들러 | 복구 단위 |
|---|---|
| `IEventHandler<T>` / `IValueEventHandler<T>` | 실패한 이벤트 |
| `IBatchEventHandler<T>` / `IValueBatchEventHandler<T>` | 실패한 `OnBatch` 호출의 연속 span 전체 |

링 끝을 넘으면 배치가 두 조각으로 나뉠 수 있다. 두 번째 조각의 Retry는 첫 조각을 반복하지 않으며,
Halt는 첫 조각의 완료 위치를 보존한다. 첫 조각을 Skip해도 두 번째 조각은 처리한다. 실패한 조각 안에서
이미 발생한 부수 효과는 알 수 없으므로 재시도는 조각 전체에 대해 멱등해야 한다.

Skip은 롤백이 아니며 후속 의존 핸들러가 진행할 수 있다. 업무상 거절은 데이터로 표현한다.
Halt는 해당 처리기를 멈추지만 게이팅 시퀀스는 남아 생산자가 막힐 수 있다. `ProcessorHalted`를
관측해 신규 유입을 중단하고 별도 제어 흐름에서 종료를 조정한다.

기본 `ResilientExceptionHandler`는 실패를 건너뛰고 연속 100회 실패 시 정지한다. 성공한 처리는
실패 횟수를 초기화하지만 Skip된 실패는 배치가 바뀌어도 초기화하지 않는다. 성공한 `OnBatch`는
조각 단위로 초기화한다. 조각 내부 개별 성공은 처리기가 알 수 없다.

이 핸들러는 상태가 있으므로 처리기별 인스턴스가 필요하다. `SetDefaultExceptionHandler`와 호스팅
빌더의 `WithExceptionHandler`는 전달된 인스턴스를 공유하므로 여러 처리기에 하나의
`ResilientExceptionHandler`를 설정하면 안 된다. 기본 설정은 처리기별로 새 인스턴스를 만든다.
일반 동기 처리기의 임계값을 바꾸려면 등록 후 `Start` 전에 각 `BatchEventProcessor<T>`에
`SetExceptionHandler`로 별도 인스턴스를 설정한다.

동기 재시도 사이와 배치 조각 사이에서 취소를 확인한다. 반환하지 않는 핸들러를 강제 중단하지는
못한다. Retry에 자동 지연이나 횟수 제한은 없으므로 반복 실패에는 제한이 있는 정책을 사용한다.

## 슬롯 소유권과 정리

DSL의 `AutoClearSlots` 기본값은 `true`다. 최종 동기 프로세서가 하나이고 최종 워커 풀이 없을 때
자동 정리를 켠다. 참조 이벤트는 `IClearable` 구현이 필요하며 값 이벤트는 `default`로 초기화한다.
최종 독자가 여러 개면 [풀 버퍼 예제](../samples/UsageRecipes/PooledPayload.cs)처럼 합류 후 정리한다.
저수준 프로세서·폴러·비동기 소비자는 소유권과 정리를 직접 구성해야 한다.

동기 배치 핸들러는 자동 정리가 켜져 있으면 성공·Skip 조각을 정리한다. Retry·Halt의 실패 조각은
보존한다. 참조 슬롯의 `Clear()`가 예외를 던지면 오류를 보고하고 반환된 복구 정책과 관계없이
처리기를 정지한다. 완료된 업무를 반복하거나 버퍼를 두 번 반환하지 않기 위해서다. 남은 payload는
모든 독자가 멈춘 뒤 정리한다. `Clear()`는 예외를 던지지 않게 구현한다.

콜백 종료 후 필요한 값은 변경 가능한 내부 데이터까지 복사한다. 객체 참조 복사는 스냅샷이 아니다.
구조체에도 참조 필드가 들어갈 수 있으므로 인라인 저장만으로 GC 스캔·내부 객체 수명 문제가 사라지지는 않는다.

## 비동기 소비

await가 필요하면 `IAsyncBatchEventHandler<T>`와 `AsyncBatchEventProcessor<T>`를 사용한다.
콜백의 `ValueTask`가 끝날 때까지 처리 시퀀스를 전진시키지 않으므로 await 전후에 슬롯을 읽을 수 있다.
게시 전에 `AddGatingSequences`로 처리기 시퀀스를 등록한다. `IWorkHandler`를 포함한 동기 콜백은
동기로 유지해야 한다.

`AsyncWaitStrategy.WaitForAsync`는 추가 게시 없이 취소만으로 유휴 대기를 끝낸다. 생성자의
`timeout`은 동기 모니터 재확인 간격이며 비동기 타임아웃이나 주기적인 `OnTimeoutAsync`를 만들지
않는다. I/O 제한 시간은 핸들러에서 정한다. 실행 중인 비동기 작업도 취소 토큰을 관측해야 한다.

비동기 복구 단위는 동기 span 조각이 아닌 콜백에 전달된 시퀀스 범위다. Skip은 해당 범위를 건너뛰고,
Retry는 같은 시작점부터 다시 시도하지만 다음 시도의 가용 끝점은 달라질 수 있다. 부분 저장에 대한
멱등성이 필요하다. 위 동기 슬롯 자동 정리 동작이 비동기 처리기에 자동 적용되는 것은 아니다.

## 종료와 내구성

생산자 중단 및 완료 → 소비 드레인 → 자원 해제 순서로 종료한다. `Shutdown(timeout)`은 기본 5초의
제한 시간 안에 드레인을 시도한다. 드레인 시간 초과 시 경고를 기록하고 정지를 시도하며, 드레인 실패
예외나 모든 핸들러의 종료를 보장하지 않는다. 스레드 join 때문에 전체 호출 시간이 제한 시간을 넘을
수도 있다. 최종 시퀀스·미처리 건수·처리기 상태를 확인한 뒤 공유 자원을 해제한다. Generic Host도
같은 종료 경로를 사용하므로 호스트의 정상 종료만으로 무손실 처리가 보장되지는 않는다.

`Halt`는 취소이지 드레인이 아니다. 직접 관리하는 비동기 소비자는 생산 완료 → 최종 시퀀스 처리 확인 →
Halt → 실행 Task 완료 대기 → 게이팅 제거 순서로 종료한다.

저널→로직 의존 관계는 기록 순서를 제공하며 크래시 내구성을 자동 보장하지 않는다. 기록 실패 시
Skip 대신 Halt해야 한다. `flushToDiskOnBatchEnd` 기본값은 `false`이므로 응답 전에 디스크 반영이
필요한 시점을 결정한다. 결정론적 재생에는 같은 초기 상태, 시간·틱·난수 입력 기록, 호환되는 로직도
필요하다. 샤드별 시퀀스는 독립적이며 복제 전송·스냅샷·외부 부수 효과 중복 방지는 애플리케이션 책임이다.
[저널 예제](../samples/UsageRecipes/JournalReplay.cs)에서 구성 방법을 확인할 수 있다.
